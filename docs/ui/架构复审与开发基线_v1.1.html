架构复审与开发基线 v1.1

2026-09-15 · 复审基线 761d355 · 适用：SF32LB58-DevKit-LCD A128R32N1、390×450 CO5300/FT6146

现有分层方向可继续使用，但当前代码仍是经过少量加固的 SDK 演示工程。进入产品页面开发前，需要收敛生命周期、启动时间、板级来源、输入语义和构建交付。本文中的源码问题是静态检查结论；没有将其描述为已在开发板上触发的故障。

配套阅读：系统架构、功能逻辑与页面契约、模块接口与开发任务。文档 v1.1 是架构细化版本，不是新固件版本。

1. 复审结论与开发边界

继续采用 C、RT-Thread、SiFli GUI 框架和 LVGL 9.4。GUI、后台业务、平台驱动分别有唯一的状态所有者。先完成“数字表盘 → 应用列表 → 设置 → 亮度 → 返回”的纵向流程，再加入计时器与全局提醒，最后扩展蜂窝桌面和其他 App。

决定本版落实方式完成证据
先修可靠性基线M0.1 修复 A01–A03、A05，收敛 A07/A09 构建约束；A04 在 M1.0、A06 在 M1.1 处理，A08 单独上板验证。缺陷复现/回归记录、主机测试、目标构建；板测独立记录。
服务基础提前M1.0 实现时间有效性、最小命令/结果账本、会话设置和显示操作适配；M2 扩展计时、闹钟。M1 亮度操作有真实执行结果，页面不假定保存成功。
限制第一版动画默认 Q1；转场忙时保存一个返回意图，在合法完成点执行。任意中途反向动画在 SDK 行为验证后加入。连续点击、返回、弹层抢占不会重复提交路由或提前释放资源。
离线范围可执行本地工具做真实业务；缺少传感器/电池硬件时返回能力状态；在线 App 使用独立演示数据。界面、状态栏和历史记录都能区分真实、样例与未知。
首期资源有硬上限8 个计时器、16 个闹钟、24 个提醒槽；GUI 栈 16 KiB，新增服务栈 4 KiB。容量测试和内存账本；数字是项目预算，不是 Apple 产品限制。

可以开始 M0.1 修复和 M1.0 基础开发。新分区尚未完成实机引导验证，因此不能把构建成功作为允许刷入任意镜像组合的依据。参考 watchOS 26 的具体小版本、表冠实物和手表结构尺寸未冻结，不影响核心状态机与组件开发。

2. 源码与文档问题清单

优先级：P0 为首烧/退出崩溃相关阻断项，P1 为首个产品闭环必须处理，P2 为后续模块接入前处理。状态“待修复”意味着本次文档复审没有修改相应固件代码。

编号 / 状态证据与触发条件处理要求与验收
A01 · P0 · 本地修复，板测待执行app_clock_main.c 的 on_stop() 使用 rt_list_for_each 遍历并 rt_free(clk_desc)。宏的下一步仍访问已释放节点的 next。保存下一节点、摘链后释放；检查嵌套 deinit 的所有权。强制启动/退出至少三个表盘，内存检测器不报告释放后访问，链表最终为空。
A02 · P0 · 本地修复，板测待执行app_mainmenu.c 注册 display 级 refr_start_cb，退出未注销；回调直接解引用 p_menu_cell，而 on_stop() 将其释放并置空。保存事件描述符并在释放页面状态前注销；仅加判空不能解决反复注册。强制销毁桌面后刷新屏幕，再反复创建 100 次，回调数量回到基线。
A03 · P1 · 本地回滚路径已补，覆盖边界见实施记录表盘 on_start() 分配后直接 memset；app_clock_register() 分配后直接写字段。桌面多处用断言处理分配失败。逐次失败注入；构造失败按逆序清理，恢复到预先建立的轻量错误层。禁止在内存不足路径上再次分配整屏兜底资源。
A04 · P1 · 待修复watch_demo.c 的 app_watch_entry() 每次启动执行 set_date(2022, 7, 1) 与 set_time(9, 0, 0)。改为读取 RTC 状态和校时记录；保留有效时间，无效时显示待校时。重启不能重设已确认时间；没有备份供电时明确失效。
A05 · P1 · 本地修复，P95 板测待执行GUI 主循环直接按 lv_timer_handler() 的返回值休眠；架构写了活跃等待上限 20 ms，代码尚未落实。新增统一等待适配，正确处理无定时器哨兵和 tick 换算。服务唤醒位可合并，GUI 每次醒来都重新拉状态；不得使用无上限等待阻塞已入队输入。
A06 · P1 · 待实现应用只对 BSP_KEY1_PIN 调用 button_init()；KEY2 虽在 board.conf 声明，未接应用回调。当前队列门控只有单键，M0 点击直接映射 Home。KEY1 暂映射表冠按压，KEY2 经实物检查后映射侧键；每键独立门控、独立序号。M1 引入双击识别时必须关闭旧的即时 Home 分支，防止重复导航。旋转表冠状态仍为 absent。
A07 · P1 · 来源与构建约束已实现Keil 工程的四个基础板 bsp_*.c 指向 SDK 的 customer/boards/sf32lb58-lcd_base，不是仓库内同名副本。开发板阶段明确以锁定 SDK 的基础板驱动为准；自研 PCB 建新的项目 BSP 并验实际编译路径。禁止只修改未参与编译的副本后宣称硬件行为已变化。
A08 · P0 · 待上板验证ptab.json 已将 main 移到 0x69000000；当前板仍是旧演示固件。静态检查只覆盖已声明区域、镜像大小和下载地址。核对 NAND 几何与 SDK 地址转换、备份、写入回读、新 ftab 切换、冷启动和串口恢复。旧 main 大于旧槽，不能承诺回写旧固件时不会覆盖旧数据区。
A09 · P1 · 已加文件锁、归档及身份校验GCC 与 Keil 使用同一个 build_iwatch_sf32lb58_a128_qspi_hcpu 目录；generate-keil.ps1 只在生成前调用布局检查。本版 SDK 的 --target=mdk5 启用 no_exec，只生成工程；原来把模拟构建输出当成真实编译的说法有误。现在包装脚本单独执行实际 Keil 构建。首个发布包加入工具链、源码/配置哈希与镜像清单；每次构建后检查。分离输出目录前禁止并行构建；不能凭文件名识别镜像来源。
A10 · P1 · 文档已修正M1 依赖设置/命令服务，旧分期却把消息与时钟基础放到 M2；8 个待提醒槽无法覆盖 8 个计时器与 16 个闹钟同时触发。依赖提前到 M1.0；提醒按源预留 24 槽并可合并重复发生，普通通知另算。详见接口文档。
A11 · P1 · 历史标记已修正，板上身份待补状态页仍写屏幕待到货；文档校验清单仍引用删除的 .md；部分 HTML 表格残留百分比窄列样式。统一实际板屏基线、更新 HTML 哈希与入口、检查相互链接和浏览器呈现。历史工程 ZIP 保留归档内容与原校验值。
A12 · P2 · 接入前处理未启用的 PM/DFU 分支仍包含旧 LVGL 调用方式；当前配置不代表这些路径编译或运行通过。开启功能前迁移相关 API、明确上下文，新增该配置的构建及唤醒测试；默认关闭不会被误写成已经支持休眠/升级。

上述清单是有边界的代码审查结果，不是全仓库无缺陷结论。修改时继续核对新路径的错误处理、页内资源释放以及 SDK 的真实生命周期顺序。

4. 启动、失败降级与恢复

flowchart TD
 A["复位 / Bootloader / ftab"] --> B["RT-Thread 与 SDK 板级初始化"]
 B --> C["核心池、能力表、时间有效性"]
 C --> D["创建唯一 GUI 所有者"]
 D --> E["显示、内置字体与轻量错误层"]
 E --> F["输入适配与最小服务"]
 F --> G["读取设置快照与资源描述"]
 G --> H{"时间可信？"}
 H -->|是| I["数字表盘"]
 H -->|否| J["待校时表盘 / 手动校时入口"]
 G --> K["存储不可用：会话模式"]
 E --> L["显示失败：串口诊断 / 保留恢复入口"]

逻辑启动顺序由一个 iw_boot 协调者管理。RT-Thread 自动初始化与 INIT_APP_EXPORT(app_watch_init) 的执行顺序需要在实现时核对，不能在两个自动入口分别初始化同一个队列或显示。输入采集启用前，队列、GUI 唤醒对象和能力表必须已创建。

阶段成功条件失败去向
B0 存储引导bootloader、ftab、main 来自同一发布包且地址/校验一致。进入已验证的串口恢复路径；当前尚无自动双槽回滚。
B1 最小运行时固定队列/账本、时间服务与诊断缓冲建立。记录启动失败阶段；不继续接收业务命令。
B2 显示就绪LCD 初始化返回成功，内置字体可用，首个 flush 完成。显示为 fault；串口可诊断。LCD 驱动本身失效时不能声称可显示屏上错误页。
B3 服务就绪最小服务线程收到启动握手；GUI 可读版本化快照。只显示时间/状态和错误入口；设置控件禁用并显示明确原因。
B4 设置恢复记录版本、长度与 CRC 正确；硬件能力允许。默认会话值；未知 schema 保留原记录；挂载失败不自动格式化。
B5 产品首页数字表盘建立；测试模式标识正确；输入释放状态同步。构造失败回到已存在的轻量错误层，不递归尝试完整首页。

启动中的单步超时和重试次数是可配置预算；没有量测前不写“保证几秒内启动”。M1 先记录 reset、GUI ready、首帧提交、flush done 四个时间戳，再制定首帧时间门槛。

预分配的轻量错误层属于 GUI 基础资源，首期预留 16 KiB 项目配额及内置小字库；不占第三个 SiFli App 名额。内存不足时只修改已存在标签、隐藏复杂内容；显示与主线程同时故障时由串口/看门狗处理，不能假设屏上恢复总可用。

5. 构建、分区与可恢复交付

规范配置链为：项目 board.conf / Kconfig、项目 ptab.json、SCons 生成的 rtconfig/链接脚本、编译器产物、下载清单。不要编辑 build 目录中的生成头文件作为长期配置。发布清单应同时保存以上输入的 SHA-256、SDK commit 与补丁列表、编译器版本、board_id、partition_version、resource_version。

对象当前值发布前要求
main 装载0x69000000，6 MiB；旧构建记录 5,709,824 B。新构建按实际大小计算，不复用旧数字；同时核对 PSRAM 运行窗口。
ftab / bootloader0x1C000000 / 0x1C020000。和 main 打包并回读验证；更换引导表前，新的 main 必须已验证可读。
NAND 数据现有 KV 槽各 16 KiB，FS 6 MiB；均属于既有表。核对页、擦除块、ECC/BBM 和虚拟地址规则。16 KiB 逻辑槽不证明有独立可擦除物理块；应用禁止绕过驱动直接擦除。
源码基线应用在仓库，SDK 外部依赖；部分基础 BSP 直接来自 SDK。记录 dirty 差异并制作可复现补丁；先做干净 SDK 构建，不直接重置现有 SDK 工作区。
双工具链目前共享输出目录。串行执行并立即记录镜像清单；后续分离 GCC/Armclang 输出，生成工程不得悄然覆盖待发布包。

首烧门槛：① 读出器件标识和容量；② 核实读取工具导出的是物理还是逻辑地址数据，保存可校验备份；③ 核对工具擦除粒度不会覆盖其他区；④ 写新槽并回读校验；⑤ 使用匹配 ftab 引导，验证冷启动；⑥ 演练进入下载模式并恢复匹配的已验证固件包。若任一步依赖的读取/恢复能力尚不存在，记录阻断项，不用“有旧 bin”替代可恢复证明。

不设置自动全片擦除。旧主程序超出原 4 MiB 槽，因此旧包的恢复过程必须重新核对数据影响；当前不提供原地无损升级保证。OTA、签名链和安全启动以后独立设计。

6. 开发与验收门槛

门槛允许推进必须具备
G0 文档可开发开始 M0.1、M1.0 核心代码。页面/业务状态、接口所有权、容量、异常与任务依赖已写清；未验证事项有编号。
G1 基础代码可集成进入 M1.1 组件、路由和输入集成。A01–A05 修复与回归、A07/A09 构建检查；M1.0 最小服务流程和有效时间保留通过。A06 的复合输入在 D09 完成，并在 G3 前验收。
G2 镜像可上板烧录一个确定的固件包。布局、大小、下载地址、备份与恢复方案闭环。G1 通过不自动代表 G2 通过。
G3 首个闭环可扩展计时器/提醒和系统壳层。表盘→设置→亮度完整路径及错误路径通过；快速导航无残留；缺失硬件状态正确。
G4 可以长测低功耗、持久化、8 小时混合测试。监督/故障注入、计时恢复、存储提交语义和设备超时已独立验证。

当前 G0 文档已细化；G1–G4 未通过。D01–D03 实现与主机、构建、板上三栏状态见 实施记录。D04/D05 尚未完成，因此不能把基础修复提交宣称为 G1 通过。

7. 依据与适用版本

源码依据为本仓库 761d355 与本地 SDK 421126d9：rtos/rtthread/include/rtservice.h 的链表宏、middleware/include/gui_app_fwk.h 的公开页面/动画 API、生成的 Keil FilePath 和下载清单。后续修改源码时需同步更新本页状态。

单一 GUI 入口与队列传递快照遵循 LVGL 9.4 线程说明。按键基础语义参考固定版本的 watchOS 26 按钮与手势及 打开 App；本项目的数值阈值、离线降级和容量限制属于自己的实现规范。
