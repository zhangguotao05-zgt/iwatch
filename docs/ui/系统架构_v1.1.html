iwatch 系统架构 v1.1

日期：2026-09-15。基准：SF32LB58 开发板、390×450 CO5300/FT6146 模组、SiFli-SDK v2.5.1、LVGL 9.4.0。

本文确定后续实现的边界和约束；除明确列入实施记录的部分，其余均为设计。界面覆盖范围见 UI 复刻计划，像素与动效规范见 视觉与交互规范，落地次序见 实施与验收。

本次修订补充了源码审查、M1 服务依赖、命令结果保留、24 槽提醒容量和可实现的转场策略。配套文件：复审问题与开发准入、功能逻辑与页面契约、模块接口与开发任务。协议字段、状态转换和测试编号以这三份细化文档为准；本文保留总体结构。

1. 架构决定

采用 C + RT-Thread + SiFli GUI 应用框架 + LVGL。应用、系统壳层、后台服务和设备适配分开，项目核心逻辑保持可在 PC 上测试。第一阶段运行离线功能；联网、官方 App 执行环境不在本架构实现范围。

决策 实现规则 解决的问题
单一 GUI 所有者 app_watch 独占页面、LVGL 对象、导航和动画操作 避免线程同时删改控件产生崩溃
延用 SiFli 应用框架 App 启停、子页面、转场沿用 gui_app_*；项目路由层只做策略和校验 避免两套页面栈互相冲突
后台服务拥有业务状态 秒表、计时器、提醒、设置、采样状态不放在页面对象里 页面销毁后任务仍继续
明确的消息协议 命令、回执、状态快照均有固定结构、容量、版本和错误值 不通过任意指针和字符串广播耦合模块
有限资源 队列、页面栈、缓存、后台任务都有上限；超过上限有明确退路 控制长期使用中的内存增长
可降级视觉 三档统一渲染质量，共用布局、颜色、输入和业务代码 动效负载过高时仍保持可用
能力与数据质量显式建模 available / absent / fault / initializing；数据区分有效、陈旧、样例和未知 不把样例心率、电量或连接状态当成实测值
芯片与板型隔离 页面不写 GPIO、I²C 地址或 FPC 引脚；由本板适配层提供能力 后续自研 PCB 更换电源、触摸或按键时局部改动

LVGL 文档说明了多线程并发访问的约束；本项目选择单一线程入口。LVGL 9.4 线程说明

3.1 已发现的布局问题

自研原理图选型为 SF32LB586VDD36；当前板型 rtconfig.py 的 PACKAGE='SF32LB587' 是 SDK 编译选择，不能替代实物料号核验。当前生成的 Keil 工程仍从外部 SDK 引用四个 bsp_* 源文件，仓库内存在同名副本并不代表它们参与构建。版本、路径和 SDK 工作区差异见 复审基线。

当前项目分区来源为 firmware/iwatch/project/iwatch_sf32lb58_a128_qspi_hcpu/ptab.json，不能只看通用板级 ptab.yaml。

  • PSRAM1 原配置为代码 6 MiB + 数据 12 MiB，总计 18 MiB，超过板级配置的 16 MiB。第一批修改将数据区收敛至 10 MiB，并在构建前检查边界。
  • 修改前 PSRAM 中代码运行窗口为 6 MiB，NAND 中 main 镜像装载槽只有 4 MiB。进一步读取发现本地 main.bin 为 5,709,092 B，约 5.45 MiB，按旧下载地址会越过 KV 区并进入文件系统范围。尚未读出板上 NAND 内容，不能由此断定实际保存了哪些数据或哪些数据已经损坏。
  • 主文件系统分区是 6 MiB；32 MiB 的资源空间只能作为未来重新分区目标。扩容必须同步启动表、烧录脚本、文件系统、坏块处理与迁移方案。
  • 历史 flash1 FAL 缺失提示仍待解决。在挂载和掉电恢复验证通过前，设置只能报告为本次会话有效，不宣称已永久保存。

本地 v1 配置将 main 装载槽移到 NAND 偏移 0x01000000（16 MiB），地址 0x69000000，大小 6 MiB；现有 KV、FS、FS_EX、ACPU 和启动 NOR 的地址保持原值。该区域在当前完整表中没有其他分区，且位于配置的 128 MiB NAND 内。第一批同时增加布局/镜像/下载地址检查。

这是待上板验证的新布局；当前板上没有执行迁移。首次烧录前必须导出旧 flash table、数据区与现有固件，并确认实际 NAND 型号/容量及 SDK 的地址转换。随后验证新槽写入、校验、启动表切换和回滚路径。不能只替换 main.bin 后沿用旧烧录地址；源码检查通过不能替代新地址的实机引导验证。

4. 线程与调度

RT-Thread 优先级数值越小越高。新增线程下表是起始预算，必须通过高负载栈峰值和执行耗时测量确认。

执行上下文 优先级 / 栈 负责 禁止
IRQ / SDK 定时回调 SDK 配置 记录输入、完成标志，发非阻塞消息 LVGL、文件操作、等待锁、日志洪泛
SDK 触摸 / LCD 10 / 1 KiB；12 / 2 KiB 输入采集和显示传输 应用业务与文件存储
iw_super，后续新增 15 / 2 KiB 心跳检查、错误计数、受控恢复 固定无条件喂狗、重渲染页面
iw_service，M1.0 引入 17 / 4 KiB M1.0：命令、时间、设置与快照；M2：计时期限和提醒调度 阻塞存储和渲染；一轮持续占用 CPU
app_watch，已有 19 / 16 KiB 输入消费、导航、LVGL、显示状态 同步读大图片、轮询传感器、等待服务回执
iw_io，按需求新增 22 / 4 KiB 文件、配置日志、资源预读；分块执行 持有 GUI 锁或 LVGL 对象

服务线程处理完批次就等待消息或最近期限；单次 CPU 工作目标不超过 1 ms。GUI 每轮最多处理 8 条离散事件或 2 ms 的事件工作，随后进入 LVGL。GUI 活跃时等待上限 20 ms，避免 LVGL 空闲等待过长导致按键长期无人消费；若渲染占用过长，先测量再优化，不能靠提高 GUI 优先级解决。

新增工作线程按阶段引入，不一开始为每个 App 建线程。深睡时的期限由 RTC/AON 唤醒源承担；关闭显示不关闭正在运行的提醒业务。

5. 数据流与消息契约

5.1 命令和快照

服务接口使用明确类型，典型命令为 TIMER_START、TIMER_CANCEL、SET_BRIGHTNESS、SAVE_SETTING。命令为固定 32 B，带 session_id / request_id / page_id / page_generation、协议版本和按值复制的短载荷；回执带请求键、错误码与状态版本。照片等大数据另用有引用计数和容量上限的资源句柄传递，不能发送局部变量指针。字段和接口见 命令契约。

统一错误类型：参数错误、忙、队列满、设备不存在、设备故障、结果待确认、存储不可用、资源不足。入队成功只表示 QUEUED；执行完成和持久化分别确认。超时不是失败或撤销：同一服务会话内以相同请求键查询或重试，不重复新增闹钟。结果账本满时在执行前拒绝新请求；已确认的旧请求通过序号水位防重放，不能因记录淘汰再执行。服务重启后重新核对模型，不承诺跨断电恰好执行一次。

建议容量与溢出策略：

通道 初始上限 满时行为
按键离散输入 16 条 丢弃新事件并计数；GUI 发现溢出时重置按键组合状态并要求先释放再接收新按压，防止卡住或误触发
UI→服务命令 16 条 返回 BUSY；控件保留原状态，给出轻提示
服务→UI 完成提示 16 条 只是唤醒提示；终态保存在 32 槽结果账本，最多 16 个未完成请求。GUI 全局消费器查询、确认，不能由已经退出的页面负责清理
高频状态 每主题一个最新快照 合并为最新值；传感器采样缓存另行管理，不能为每个样本强制重绘
待处理提醒 固定 24 槽 为 8 个计时器和 16 个闹钟各保留一槽，普通通知另设 32 槽。未确认提醒不能被普通通知挤掉；同来源重复发生合并并累计 missed_count

单项设置采用“请求中→已应用→已持久化/仅本次有效”状态。UI 不在发命令后立即假定硬件执行成功。UI 读快照时短锁复制或使用经测试的双缓冲交换；裸 volatile 不承担并发同步。

5.2 一次计时器操作

每个快照携带采样时间、数据来源和质量。硬件未接入显示“未连接”或 --，演示数据在相关页面明显标注“演示”。不通过随机变化的数据假装实测心率/血氧。

6. 导航、页面与生命周期

6.1 所有权

项目 navigator 是 SiFli 框架的入口门面：检查页面 ID、能力、锁屏条件、栈深及转场状态，再调用 gui_app_run/create_page/goback。它不复制 SiFli 的实际运行栈。应用切换器维护的是最多 6 项的历史模型，不要求 6 个应用都留在内存。

  • 同时最多 2 个 App 保持运行对象；转场期间允许前后两页共同存在。
  • 单个 App 子页面深度上限 8；超出时拒绝打开并记录问题，不丢弃当前页面。
  • 系统叠层最多 1 个交互弹层；通知横幅另设一个有限槽，新的同类提示合并。
  • 缓存遵循预算，后台 App 可被销毁；恢复时从业务状态和页面位置重建。
  • 每个异步请求携带 {page_id, generation}。旧页面的显示结果不再投递；全局结果消费器仍完成服务结果确认及资源释放，不能写入新页面同名控件，也不能把业务结果一起遗失。

6.2 与 SDK 生命周期对应

SiFli 事件 项目动作
ONSTART 创建页面作用域；分配有上限的控件、订阅和资源；失败则显示轻量错误页
ONRESUME 读取最新快照；恢复必要动画/刷新；按是否可见申请性能与显示唤醒
ONPAUSE 暂停不可见的动画和刷新；保存滚动位置，撤销可取消的页面资源请求。已接受的设置、计时和保存命令继续执行，由全局消费器接收结果
ONSTOP 先使 generation 失效，再撤销订阅/回调，释放页面作用域和资源句柄；允许重复清理

LVGL 动画、定时器、事件订阅、异步请求和缓存引用都必须登记在页面作用域。删除根控件不能替代全部清理。内存紧张时先释放后台缓存；单次重试仍失败就恢复到常驻简洁表盘/错误界面，不能递归重试分配。

首版转场策略为单事务加一个 pending 返回：正在转场时不再开始第二次栈变更，返回请求合并一次，当前公开框架事务收敛后立即执行。资源失败恢复到已提交页面；完成与取消只提交一次。真正的中途反向接续须验证 SDK 公开 API、回调顺序和所有权后另行开启，不能直接修改框架私有栈。任何表盘都不能自行接管控制中心或全局锁屏。

7. 输入、时间与电源

7.1 输入

FT6146 触摸走现有 LVGL 输入驱动；手势仲裁由 GUI 所有者完成。按键/表冠回调只上报事件。M0 已将按键活动通知移入 GUI 队列消费；当前仅注册 KEY1，KEY2 与旋转输入尚未接入。M1 以 PRESS/RELEASE 构建单击、双击和长按，忽略 SDK 的复合 CLICK/LONG 事件，并移除 M0 的立即 Home 分支，防止同次操作执行两遍。

触摸状态机为 IDLE→PRESSED→DRAG/SCROLL/LONG_PRESS→RELEASE/CANCEL。移动超过阈值后取消长按，拖动后不再点击；水锁过滤触摸但保留退出水锁的物理按键入口。屏幕方向变更由同一坐标变换映射处理。

单/双击有统一时间窗；不能第一次点击已打开控制中心、第二次又同时打开钱包。视图可立即显示按下反馈，单击导航等双击窗口结束才提交。旋钮原始增量先防抖、限速，再转成滚动/缩放语义。起始参数见视觉规范，通过实物调节；软件命令入口只用于测试，不能算物理表冠已验证。

7.2 两种时钟

  • 日历、日期、闹钟时刻使用 RTC 墙上时间，并带时间有效性和时区。
  • 秒表和正在运行的倒计时使用 64 位单调时间，避免用户改时间影响已运行时长。
  • RTOS 32 位 tick 的扩展只由一个服务更新，处理回绕；休眠恢复使用已验证的低功耗计时源补偿，不能默认 rt_tick_get() 在深睡中连续。
  • M1.0 必须删除每次启动将 RTC 改成 2022-07-01 的示例逻辑；当前源码仍保留此行为。只有无效时钟才进入设置时间流程，历史固定日期本身不能作为时钟可信的证据。
  • 重新上电没有可信 RTC 时，不能猜测断电经过时间；保存的计时器显示“计时需确认”。闹钟防止时钟回调引发重复提醒；大幅改时间采用重新计算并告知用户的策略。

7.3 电源状态

目标状态为 ACTIVE→DIM→SCREEN_OFF→SLEEP，充电、正在显示提醒、存储提交、显示 DMA 等通过有时限的唤醒锁阻止不合适的迁移。等待刷新完成、保存必要状态后才能关闭屏幕/电源。恢复顺序为时钟与总线→设备→触摸清状态→单调时间补偿→页面快照→首次刷新。

当前第一阶段先稳定 ACTIVE。后续先验证灭屏再验证睡眠；不把“黑色画面”当作进入低功耗。缺少电池计量数据时状态为未知，避免使用示例固定 100%。

8. 内存、资源和刷新预算

单位 KiB/MiB 分别为 1024/1024² 字节。以下为目标上限，必须在链接、运行峰值和资源清单中实际落账。

项目 v1 预算 / 要求

双 50 行 RGB565 绘制缓冲 390×50×2×2 = 78,000 B，由现有显示适配拥有

显示带宽核算：全屏 RGB565 每帧 351,000 B，30 fps 约 10.53 MB/s，60 fps 约 21.06 MB/s。现有接口报告理论 25 MB/s，60 fps 已接近传输上限，还没有计入渲染和等待。因此 常见页面以稳定 30 fps 验收，60 fps 是局部滚动/转场的优化目标。

先局部刷新、预解码和复用对象，再考虑加大缓冲。列表只保持可见行与少量预取行；图表用定长环形历史。大字号数字和图标用预生成资源，减少运行时字体光栅化。RGB565 的浅色透明层和渐变用板上色阶图检查，必要时预烘焙抖动。

DMA/EPIC 可用内存、缓存行对齐、clean/invalidate 和完成通知均由底层适配负责。GUI 不能在传输尚未完成时释放或覆盖源缓冲；不能把普通任意 PSRAM 指针默认视为 DMA 安全。

看门狗第一阶段只采集心跳，先测量合法的最长阻塞路径，再确定阈值。深睡采用显式批准状态，不能误报正常睡眠。看门狗不能只由高优先级线程无条件喂养，否则 GUI 死锁仍无法被发现。

持久化采用有版本、序号、长度和 CRC 的 A/B 记录。只有新记录完整校验且提交成功才成为当前版本；旧记录保留到下一次安全回收。A/B 逻辑必须运行在已经验证的 NAND 坏块/ECC/文件系统层之上，且验证物理掉电时的隔离与提交语义；不能凭 rename() 或 CRC 就宣称掉电安全。写入按防抖批量提交，避免每帧、每秒写闪存。升级遇到未知 schema 时保留旧记录并进入兼容降级。

诊断保留有限 RAM 环形日志、构建 ID、分区版本、内存高水位、消息统计、页面转场耗时、输入到首帧耗时及显示完成时间。串口日志限频，不能每个触摸样本打印。生产显示层不出现驱动实现细节；详细原因留在诊断页和日志。

10. 迁移边界与完成标准

先保留已点亮的 CO5300/FT6146 BSP。M0.1 修复现存生命周期问题并核对构建来源；M1.0 建立时间、命令回执、RAM 设置和亮度适配；M1.1 建立主题组件与路由，M1.2 完成“表盘→桌面→设置→亮度→返回”；M2 再扩展计时器、秒表、闹钟。详见 D01–D18 任务依赖，先通过基础闭环再扩展 App 和表盘。

现有 app_mainmenu.c、app_clock_main.c 的示例注册和资源逐页迁移；不一口气删除已工作的入口。每迁移一个 App 就给它补上可达路由、错误状态、资源清理和板上性能记录。每个版本必须声明“已实现、编译验证、板上验证、待实现”，四项不能混为一谈。

架构 v1 的主要决定已确定。待实物调定的参数是触摸阈值、按键时间窗、动效质量档、实际并发缓存、唤醒源与看门狗阈值；这些参数调整不改变模块所有权。
