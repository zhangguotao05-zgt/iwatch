iwatch SF32LB58 固件

这里保存本项目可修改、可提交的固件源码。基线来自 SiFli-SDK v2.5.1 的 example/multimedia/lvgl/watch_v9。当前验证平台为 SF32LB58-DevKit-LCD、A128R32N1、QSPI 屏接口、A1 修订，CO5300 + FT6146 模组已点亮。DEV_A128_NAND 的 D01–D06 已完成主机、双工具链和开发板验收；D06 的 GCC 三件套已写入并校验，真实亮度、会话复位和输入压力通过。证据见 D01–D03、D04–D05 与 D06 实施记录。

D07 已按 9088f52 审批收口，性能遗留跟踪 Issue #8。当前 D08 路由实施已按“接受已知风险”收口，验收基线 5c51f54、固件源码 82ab706。基础实现及已验证功能通过，负责人同意继续 D09；半黑半白转入 #10，未定位、后续未复现，性能遗留继续跟踪 #8。首次异常、采集缺口及原始证据保留；此决定不代表显示异常已修复或产品发布验收通过。此次收口未改固件、未重新烧录。

D09 双键与输入仲裁正在实施，Issue #11 未关闭。当前记录分别维护主机回归、双工具链与本轮镜像实机结果。

依赖

  • SiFli-SDK v2.5.1，构建脚本默认本机路径：C:\OpenSiFli\SiFli-SDK-v2.5.1-iwatch-locked；也可显式传入干净 SDK 的 -SdkPath，入口严格检查固定提交及子模块
  • GCC 构建环境由 SDK 的 export.ps1 提供
  • Keil MDK5/Arm Compiler 6；本机已检测到 D:\keil\MDK5.36

SDK 作为外部依赖使用，构建缓存和整个 SDK 不提交。应用代码、板型配置和分区表在本目录；Kconfig 与四个公共 BSP 源文件仍来自 SDK。D02 已把 SDK 固定到提交 421126d9f476ed8e2a6f0b0ca28a9f241c182e65，同时固定子模块、公共 BSP 文件哈希和有效 Kconfig。构建入口只接受干净固定 SDK，或由 sdk_patch.py 验证过的 D07 派生 SDK；后者的补丁与补丁后文件哈希进入构建身份。其他脏 SDK、来源或配置漂移均拒绝。

SiFli SDK v2.5.1 的 Windows Kconfig 工具不能直接处理含中文的工程路径。如果仓库所在路径含中文，构建脚本会自动创建纯英文目录联接 C:\OpenSiFli\_workspaces\iwatch 并从该入口构建；它仍指向本仓库中的同一份文件，不会复制源码。仓库本身处于纯英文路径时会直接构建。

GCC 构建

在仓库根目录执行：

.\firmware\build-gcc.ps1

使用其他 SDK 路径时：

.\firmware\build-gcc.ps1 -SdkPath D:\path\to\SiFli-SDK-v2.5.1

工作输出位于 firmware/iwatch/project/build_iwatch_sf32lb58_a128_qspi_hcpu/，受检查归档位于 firmware/iwatch/project/artifacts/DEV_A128_NAND/gcc。归档包含主程序、Bootloader、Flash Table、map、有效配置、下载清单和构建身份。

GCC 构建与 Keil 生成共用这个输出目录，必须顺序执行。两个包装脚本在持有构建锁后都会校验并完整清理该确定目录，再执行构建、检查实际 map 工具链来源并复制到各自归档；遗留的另一工具链 map 不能通过身份校验。不能并行生成，也不能将不同归档的 main、bootloader 和 ftab 混合下载。

构建脚本在编译前校验内存布局，编译后核对镜像长度和下载地址。main 的 NAND 装载地址为 0x69000000，装载槽 6 MiB；PSRAM1 划分为 6 MiB 代码窗口 + 10 MiB 数据窗口。开发板已切换到这份布局，main 与 FTab 独立回读匹配归档，冷启动通过。回滚备份与精确哈希见 板上验收记录。

串口烧录只使用同一归档中的三件套。先执行只读检查；安装 Mode 跳帽并复位后，再执行正式命令。脚本使用 CH342 串口，不访问 J-Link：

.\firmware\flash-serial.ps1 -Port COM9 -Toolchain gcc -DryRun
.\firmware\flash-serial.ps1 -Port COM9 -Toolchain gcc

完成后取下 Mode 跳帽并复位。不要单独替换 main 或 FTab：两者元数据不匹配时会导致应用不启动、屏幕不亮。

Keil

首次打开或新增/删除源码后，先生成工程：

.\firmware\generate-keil.ps1

随后使用 Keil 打开：

firmware/iwatch/project/project.uvprojx

生成脚本会把当前 -SdkPath 写入 Keil 工程，补充 SF32LB58 的 CDE 编译参数，并检查全部源文件引用。当前工程已包含 iw_time、iw_service、iw_service_runtime、iw_boot 和 iw_time_rtc，并保留 Iwatch_core、Iwatch_gui_core 与 Iwatch_platform 分组；换电脑或改变 SDK 位置后重新运行脚本即可。

generate-keil.ps1 先生成工程，再执行真正的 Arm Compiler 编译。SDK 的 --target=mdk5 自身启用 no_exec，日志不能作为已编译证据。脚本已加入互斥锁、构建后布局/地址/有效配置/编译器标记/哈希检查及工具链独立归档。该检查不证明实际 NAND 几何、坏块处理或已有数据完整。

Keil 工程用于编辑和编译 HCPU 应用。当前开发板的 CH342 USB 串口下载仍使用 SiFli 的串口烧录脚本；Keil 的 Download 按钮需要另接 J-Link/CMSIS-DAP 并配置对应 Flash 算法。

当前板级修正

HCPU 和 LCPU 的 board.conf 均启用了 CONFIG_LCPU_CONFIG_AUTO=y，解决实物 A1 芯片使用原始 V2 配置时的启动断言。构建生成的最终编译宏可能显示 LCPU_CONFIG_V1，这是 AUTO 针对当前芯片生成的正常结果。

触摸读取线程使用仓库中的 iw_drv_touch.c，栈固定为 2 KiB。SCons 和 Keil 工程都会排除 SDK 原始 drv_touch.c，保证只有一个实现。D04/D05 最终压力窗口中的 tpread 栈峰值为 39%；此前 1 KiB 配置测得 78%，已超过门槛，不再使用。

历史启动日志中的三个 flash1 is not found 来自 SDK 默认 FAL 分区表；当前 UI 可启动不代表持久化可靠。在实现偏好数据库和资源文件系统前，需要补充本板专用 FAL 分区定义并验证 NAND 坏块/ECC 与掉电恢复。

Windows 主机测试需要 Visual Studio C/C++ 工具和 Python 3.13；脚本同时在 Windows PowerShell 5.1 下进行语法解析，JSON 文件按 UTF-8 显式读取：

.\firmware\tests\run-core-tests.ps1

D07 主机验证需固定 FontTools 4.65.0 和受控派生 SDK。下面的入口验证字符输入、两次生成、GCC/Keil 预算解析、A1 的 38 个字体内存失败点以及 B 字体服务新增故障路径、1,000 次生命周期、长通知缓存淘汰及 4,046 次 EPIC 字形像素提交；它不构建或烧录固件：

python -m pip install -r firmware/requirements.txt
python firmware/sdk_patch.py prepare --base-sdk <fixed-sdk> --output <derived-sdk> --init-submodules
.\firmware\tests\run-d07-a0-tests.ps1 -PythonPath <python.exe> -PatchedSdkPath <derived-sdk>

也可以单独运行只读布局检查；第二条必须指向与本次镜像匹配的完整输出目录：

py -3.13 firmware/check_layout.py
py -3.13 firmware/check_layout.py --build-dir firmware/iwatch/project/build_iwatch_sf32lb58_a128_qspi_hcpu

手动直接运行 SCons 或从 uVision 编译时仍需执行相应的布局和实际镜像检查；包装脚本的通过结果不覆盖之后手动修改的分区或产物。板上可用 iw_input_stat_reset 清零本轮输入统计，再用 iw_input_stat 查看计数、队列高水位和 P95 消费延迟。
